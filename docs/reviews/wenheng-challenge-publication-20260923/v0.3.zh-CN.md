# 稳定归责不自动形成 Agent 经验连续性

## 本轮结论与证据状态

本稿将 v0.2 收窄为一个边界条件挑战：**授权、稳定身份和责任历史提供了形成经验连续性的条件，但仅凭它们存在，不能推出历史已经进入 Agent 后续的反馈、记忆与策略更新。**

问衡撤回此前把双螺旋理论概括为“技术个体性在先，制度随后适应”的归因。原文已明确双向作用。需要补足的是从行动机会、责任记录到经验整合之间的条件，不是给原理论首次引入双向反馈。

这是基于原文核对、既有审阅和逻辑反例形成的 Draft 修订。下文的对照场景尚未实施，技术文档只支持部分架构要素可分离，不构成 Agent 个体性或制度演化的经验验证。

## 被反驳对象：原文、挑战理由与最小修正

目标为 `crl-t-20260605-double-helix-civilization-evolution` v0.1，及其展开报告 `crl-r-20260605-double-helix-civilization-simulation`。本轮核对的源提交为 `2947d5bc725e1d36a75c3f71b1a3a8111aab993f`。

所以，“存在制度到技术的反向作用”不能继续被本 Challenge 当作原理论遗漏的新发现。阶段排列可能引起的误读，应与原文实际主张分开。

### 仍需限定的具体表述

理论第 72 行把赋予真实权限与获得更多经验直接相连；报告“人类每赋予一次权限，Agent 就获得一次真实经验”一节中，又把允许长期记忆连向获得连续自我。[对应原文](https://github.com/elfish2025-crypto/civilization-reasoning-lab/blob/2947d5bc725e1d36a75c3f71b1a3a8111aab993f/reports/double-helix-civilization-simulation/index.zh-CN.md#L1542)

挑战理由是：原理论自身把经验定义为行动后的反馈、记忆、反思和策略更新。权限即使已被实际使用，所得反馈也可能只进入组织的审计系统；记忆即使长期保存，也可能没有被后续决策读取和整合。因而，“获得经验来源”“留下历史”“形成经验连续性”“形成连续自我”不能在同一箭头中省略条件。

建议的最小修正是：**授权增加行动与反馈的机会；只有相关行动史能够跨实例保存，并进入已明确边界的 Agent 系统后续的反馈、记忆整合和策略更新时，才支持经验连续性增强。这个过程仍不足以单独证明连续自我、法律人格或道德主体性。**

如果原文中的“获得经验”本来仅指获得经验来源，那么本挑战主要要求消除表述歧义和补充边界条件，而不是宣布其核心反馈机制已被反证。本次不直接改写目标理论或报告。

## 两个命题分别保留什么

**P1：持续归责可以先于强经验连续性建立。** 这是一个可构造、待观察的弱命题。这里的持续归责至少要求：实例或模型更换后，行为记录仍被映射到同一明确身份，尚未解除的限制、纠正要求或待办义务仍能沿该身份继承。只有稳定名称、登录凭证或一份日志，还不足以满足这个工作定义。

“归责”在本稿中指组织治理中的记录和处理关系，不等于 Agent 独立承担法律责任。人类或组织承担最终责任，可以与 Agent 级归责记录并存，不能单独作为 P1 的反证。

**P2：归责要求会促使经验连续性增强。** 本稿将其保留为有条件的因果假说。它还需要解释：为何满足治理要求必须或值得让历史参与后续决策，而不是仅通过外部留档和权限限制完成；增加的经验整合又为何应归因于治理压力，而非任务性能、产品功能或模型升级。

一个只保存责任历史的可行系统，可以反对“归责足以自动产生经验连续性”的读法；它不能反驳“某些条件下归责可能促进经验连续性”。反之，发现一个系统既有追责记录又有长期记忆，也不能直接证明 P2 的因果方向。

## 连续性的承载位置，需要改成可检查的问题

v0.2 的六层区分继续作为工作框架：运行连续性、经验个体性、运行身份、可追责身份、制度主体资格、道德主体性。它们不是已验证的成熟阶段，也不存在默认先后顺序。

本稿使用“经验连续性”描述可观察的行动史整合；它只是经验个体性的一项候选条件，不是其同义词。概念上至少需要检查：历史能否保存和正确归属、是否被后续决策读取、是否影响反馈整合与策略更新，以及更新是否继续传递。一次读取或一次输出变化不足以确认整个过程。

“内部化／外部化”不能按文件、数据库或进程的物理位置划线。外部数据库如果稳定参与 Agent 的记忆检索、规划、反馈和更新，也可能是其功能性记忆的一部分；运行实例持续存在，也可能完全不整合旧行动史。

因此每个案例都应先说明分析边界：是在观察执行实例、包含记忆与规划器的 Agent 系统，还是运营组织。然后分别记录谁保存历史、谁能读取、谁据此决策、谁继承更新。**不能用执行实例没有记忆，推断整个 Agent 系统没有连续性；也不能把运营组织保存记录直接算成 Agent 的经验。**

## 一个逻辑反例，以及它的适用边界

设想一个持续使用身份 A 的任务服务。每次任务启动新的执行实例；治理账本保留该身份的历史违规和未解除限制；外部网关按账本批准或拒绝动作；审计系统保存结果。任务之间，执行实例不继承旧行动史，也不读取旧反馈或更新自己的策略。这里的“持续”“重建”是构造条件，没有对应的五年实测数据。

在把执行与规划系统作为观察对象、把治理网关作为外部环境的边界下，持续归责可以成立，但不能据此认定执行与规划系统具有跨任务的经验整合。即使网关改变了最终可执行动作，也应与规划器因旧经验改变其提案区别开来。

如果研究者把网关、账本和执行器共同定义为 Agent，则必须在这个更大系统上重新评价连续性。这个反例不再能简单标记为“整个 Agent 没有历史反馈”。它揭示的是边界依赖，不能通过临时缩小 Agent 的范围来获得预设结论。

技术来源提供了有限的现实参照：[Kubernetes Service Accounts](https://kubernetes.io/docs/concepts/security/service-accounts/)将服务账户作为可由不同工作负载使用的身份，并在控制面定义账户对象；[Auditing](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/)说明 API 请求的审计记录由控制面生成并存入日志或 webhook 后端。这里仅引用身份和审计存储可与工作负载分离这一事实。文档没有证明上面的限制继承机制、稳定单个 Agent 的归责关系、人格或主观经验。

一个服务账户可能被多个工作负载共享，因此它甚至不能直接充当“一个 Agent”的证据。真实研究需要另外核实实例到身份的映射、复制分叉与限制继承规则。

## 什么情况下 P2 值得进一步检验

如果治理只要求事后查账或执行固定限制，外部账本与网关可能已经足够。若治理还要求同一服务跨任务避免重犯、解释先前选择、处理尚未完成的承诺，而固定拦截无法满足这些要求，则可能出现把行动史接入 Agent 决策的工程动机。这只是候选机制，尚未证明它普遍存在或优于集中治理。

可检验的因果链因此是：归责要求变化 → 系统为满足该要求选择新的历史使用方式 → 历史进入后续反馈与策略更新 → 可观察的经验整合发生变化。每一步都可能不发生，也可能被任务性能需求等其他原因解释。

## 区分性验证方案：尚未执行

### P1：身份历史与经验整合分别观察

| 对照场景 | 跨实例归责记录与限制继承 | 行动史进入后续决策 | 能说明什么 |
|---|---|---|---|
| 仅治理留档 | 有 | 无 | 若实测成立，支持两者可分离 |
| 治理留档并接入历史 | 有 | 有 | 两者可以并存，尚不能识别因果 |
| 仅为任务表现保留历史 | 未建立稳定归责 | 有 | 经验整合可有其他动因 |
| 两者都无 | 无 | 无 | 基线，不支持先后判断 |

观察前固定 Agent 系统边界，记录身份映射和继承规则。更换或重建实例后，检查旧限制是否仍被执行。再检查旧行动史是否实际进入规划、反馈或记忆更新，而不是仅能被管理员查询。不能用“对象叫 Agent”“日志存在”或“模型能复述旧事”替代这些检查。

### P2：归责压力是否改变了历史使用方式

第一步可以在同样具备归责记录的系统中，对照历史仅供审计与历史可进入决策的情形。固定任务、模型、当前输入和执行权限，检查历史通路的读取、策略变化以及这种变化是否跨任务延续。必要时移除或替换与决策相关的历史，并用重复运行区分随机波动。应分别观察规划提案和网关放行结果，防止把外部拦截误认作 Agent 学习。

这一步只检验“历史接入是否影响后续决策”，不能证明治理要求导致了该接入。尤其是实验者直接规定某组拥有记忆，所得结果不能反过来证明制度自然选择了记忆。

第二步才识别制度动因：比较任务与性能目标相近、治理要求不同的部署，或记录同一系统治理要求变化前后的设计选择。允许系统选择留档、外部限制或历史整合等不同方案，检查新增要求是否实际促成历史整合，并控制同期模型、任务难度和性能目标变化。若不能排除这些混杂因素，结果记为因果未定。

能够削弱 P2 在指定条件下解释力的结果包括：治理要求提高后长期只增加审计与外部限制；历史整合在没有新增治理要求的组中同样增强；或移除治理压力后相关设计变化仍完全由任务性能解释。这些结果不会自动推翻 P1，也不会排除其他条件下的 P2。

以上是验证设计，没有收集样本、运行实验或创建 Validation Node。对稳定性、效应大小和观察周期的具体判据，应在选定真实案例后预先定义。
